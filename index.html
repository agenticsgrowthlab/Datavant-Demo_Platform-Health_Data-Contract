PLATFORM HEALTH DATA CONTRACT: INTERVIEW DEMO ONLY - PRESENTATION BY NICOLE CHERNOW-MARTINEZ
This is a representation of the data that would feed dashboards used to visually manage: Availability, Performance, & Observability
01 TRANSACTION_STAGE_EVENT one event / transaction / stage
// emitted as a request moves Intake → Auth Review → Fulfillment → QC → Delivery
field
type
notes
schema_version
string
versioned from day one — new stages/verticals extend without breaking consumers
event_id
uuid
unique per emitted event
event_type
enum
"stage_status"
occurred_at
timestamp
ISO 8601, when it actually happened
ingested_at
timestamp
ISO 8601, when the platform received it — not the same moment
transaction_id
string
the business-level ROI request
correlation_id
string
ties every event/span for this transaction together across systems
vertical
enum
Provider · Payer · Legal & Insurance · Life Sciences
stage
enum
Intake · Auth Review · Fulfillment · QC · Delivery
stage_status
enum
healthy · degraded · critical
dependency
string?
nullable — which integration this stage relied on, if any
dependency_status
enum?
nullable, same enum as stage_status
latency_ms
integer
time spent in this stage
queue_depth
integer
backlog waiting to enter this stage
error_rate
float
0–1, this stage over the current window
sla_target
timestamp?
nullable — deadline this transaction must clear the stage by
02 OPERATION_EVENT start + complete pair / operation
// only where duration is felt by a person waiting — Upload, Search, Download. Not Authorization; it’s already near-instantaneous, and instrumenting it would add noise, not signal.
field
type
notes
schema_version
string
event_id
uuid
event_type
enum
operation_start · operation_complete
occurred_at
timestamp
ingested_at
timestamp
transaction_id
string
correlation_id
string
operation
enum
Upload · Search · Download
operation_status
enum
in_progress · complete · stalled
DERIVED — NOT STORED
duration_ms
complete.occurred_at − start.occurred_at. A completion timestamp alone proves the work finished; it doesn’t prove how long someone waited for it.
03 DEPENDENCY_CAPACITY_SIGNAL periodic gauge / dependency
// not tied to any single transaction — a standing resource-utilization reading, same shape a disk or queue-depth monitor would emit
field
type
notes
schema_version
string
signal_id
uuid
occurred_at
timestamp
dependency_name
string
e.g. Document Storage
capacity_used_pct
float
0–100
capacity_total
integer
unit defined by the dependency owner
capacity_growth_rate
float
rate of change, per day
DERIVED — NOT STORED
projected_exhaustion_days
computed from capacity_used_pct + capacity_growth_rate. Turns “storage is filling up” into an actionable countdown instead of a reactive alert after it’s already full.
04 PLATFORM METRICS computed, not emitted
// nothing below this line is a raw field on any event above — each is calculated from sections 01–03
time_to_detect / localize / resolve
MTTR split into three numbers, not one blended figure — collapsing them hides exactly where the delay lives
successful_fulfillment_rate
stage_status = healthy across all five stages, to the correct authorized recipient, within sla_target
proactive_detection_rate
share of resolved incidents where a degrading signal existed before an incident was manually opened
projected_time_to_sla_breach
trend-based forecast from latency_ms, queue_depth, and dependency_status
instrumentation_coverage
% of transactions with a complete stage-event trace, Intake through Delivery, no gaps
Scope: sections 01–04 support Investment #1 only. Fields for Investment #2 (unscoped — no target named yet) and Investment #3 (vertical-specific SLA, Later on the roadmap) are intentionally absent.
